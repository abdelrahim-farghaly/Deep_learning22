تشغيل الـ Backend و الـ Frontend و PostgreSQL بأمر واحد

حتى هذه اللحظة كان كل عضو يشغّل النظام بطريقته: نسخة Python هنا، ومنفذ مختلف هناك، وقاعدة بيانات ثالثة على جهاز زميله. هذا الفصل يحلّ مشكلة "يعمل عندي ولا يعمل عندك" عبر تغليف كل مكوّن في حاوية Container وربطها بأمر واحد. الهدف العملي: أن يستطيع أي عضو — أو لجنة المناقشة — تشغيل النظام كاملاً على جهاز نظيف دون تثبيت Python أو Node أو PostgreSQL يدوياً.

19.1 شرح Docker و Docker Compose من البداية

Docker: أداة تُغلّف التطبيق مع كل ما يحتاجه (نسخة اللغة، المكتبات، إعدادات النظام) في وحدة واحدة قابلة للتشغيل تسمّى Image (صورة). عند تشغيل الصورة نحصل على Container (حاوية): عملية معزولة تشبه جهازاً صغيراً مستقلاً. الفائدة أن الحاوية تعطي نفس النتيجة على Windows و Linux و macOS لأنها لا تعتمد على مكتبات الجهاز المضيف.

Docker Compose: أداة تُشغّل عدة حاويات معاً من ملف واحد اسمه docker-compose.yml. النظام عندنا يحتاج أربع حاويات (قاعدة بيانات، backend، worker، frontend) تشتغل وتتحدّث مع بعضها، وبدون Compose كنّا سنكتب أربعة أوامر طويلة وننسى ترتيبها. Compose ينشئ أيضاً network (شبكة) خاصة وvolumes مشتركة تلقائياً.

19.4 شبكة الحاويات: أسماء الخدمات بدل localhost

هذا أهم مفهوم يجب أن يفهمه الفريق قبل كتابة أي ملف. داخل شبكة Docker، كل حاوية لها عنوان IP خاص، ولا يمكن استخدام localhost للوصول إلى حاوية أخرى، لأن localhost داخل حاوية الـ backend يشير إلى الـ backend نفسه لا إلى قاعدة البيانات. لذلك نستخدم اسم الخدمة كاسم نطاق داخلي: الحاوية db تُنادى باسم db، والـ backend يُنادى باسم backend.

الخطأ الأشهر

كتابة DATABASE_URL=...@localhost:5432/... داخل حاوية الـ backend. هذه القيمة صحيحة عند التشغيل المباشر على الجهاز، لكنها خاطئة داخل Docker ويظهر خطأ connection refused. القيمة الصحيحة داخل الحاويات تستخدم اسم الخدمة db. أمّا من المتصفح على الجهاز فنستخدم localhost لأن المنافذ منشورة (published) على الجهاز المضيف.

19.5 الـ Volumes: كيف تصل ملفات الـ Models والفيديوهات للحاويات

الحاوية قابلة للحذف، ولذلك لا نضع فيها شيئاً نفقد فقدانه. ثلاثة أنواع من التخزين في مشروعنا:

  • pgdata (named volume): يحفظ ملفات PostgreSQL فيبقى كل شيء بعد إعادة تشغيل الحاوية.
  • storage: مجلد مشترك بين الـ backend والـ worker يحتوي الفيديوهات المرفوعة (uploads) وصور الدليل (evidence) والتقارير.
  • models (bind mount للقراءة فقط): يُربط بمجلد ./models على الجهاز، لأن ملفات الـ checkpoints كبيرة ولا تُرفع إلى Git ولا تُنسخ داخل الصورة.
لماذا bind mount للـ models؟

لأن مسار الـ checkpoint يُحدَّد من متغيّر PPE_MODEL_PATH و FIRE_SMOKE_MODEL_PATH. ربط المجلد يجعل تغيير الـ checkpoint عملية نسخ ملف بسيطة دون إعادة بناء الصورة. نضع :ro لضمان أن الحاوية تقرأ ولا تكتب.

19.6 ملف الـ Backend Dockerfile

صورة الـ backend مبنية على Python 3.11، وتُثبّت المتطلبات أولاً ثم يُنسخ الكود، لأن Docker يخزّن كل خطوة مؤقتاً (layer cache) فلا يعيد التثبيت عند تغيير الكود فقط. نستخدم الـ worker نفس الصورة مع أمر تشغيل مختلف.

backend/Dockerfiledockerfile
# SafeVision AI - backend image (also used by the worker service)
FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

# System libraries required by OpenCV and psycopg
RUN apt-get update && apt-get install -y --no-install-recommends \
    libgl1 libglib2.0-0 curl \
    && rm -rf /var/lib/apt/lists/*

# Install Python dependencies first so the layer is cached
COPY requirements.txt .
RUN pip install --upgrade pip && pip install -r requirements.txt

# Application code
COPY . .

EXPOSE 8000

# Default command runs the API; the worker overrides this in compose
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

19.7 ملف الـ Frontend Dockerfile

نبني الواجهة في مرحلة أولى (builder) ثم ننقل الناتج الثابت إلى صورة nginx صغيرة. هذا نمط multi-stage build ويقلّل حجم الصورة كثيراً، لأن Node و node_modules لا تدخل الصورة النهائية. قيمة VITE_API_BASE_URL تُثبَّت وقت البناء لأن Vite يدمج المتغيّرات في ملفات الإنتاج.

frontend/Dockerfiledockerfile
# SafeVision AI - frontend image (multi-stage build)
# ---- Stage 1: build the static assets ----
FROM node:20-alpine AS builder
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
# Vite inlines env vars at build time, so it must be present here
ARG VITE_API_BASE_URL=http://localhost:8000
ARG VITE_ENABLE_AUTH=false
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
ENV VITE_ENABLE_AUTH=$VITE_ENABLE_AUTH
RUN npm run build

# ---- Stage 2: serve the static files ----
FROM nginx:1.27-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

19.9 ملف docker-compose.yml

هذا الملف هو قلب التشغيل. لاحظ ثلاثة أمور: أسماء الخدمات (db, backend, worker, frontend)، وDATABASE_URL الذي يستخدم اسم الخدمة db، وdepends_on مع فحص الصحة healthcheck لضمان أن الـ backend لا يبدأ قبل جاهزية قاعدة البيانات.

docker-compose.ymlyaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - safevision-net

  backend:
    build: ./backend
    env_file: .env
    environment:
      # Inside the network the host name is the service name, not localhost
      DATABASE_URL: postgresql+psycopg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
    ports:
      - "8000:8000"
    volumes:
      - ./storage:/app/storage
      - ./models:/app/models:ro
    depends_on:
      db:
        condition: service_healthy
    networks:
      - safevision-net

  worker:
    build: ./backend
    command: ["python", "-m", "app.workers.main"]
    env_file: .env
    environment:
      DATABASE_URL: postgresql+psycopg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      WORKER_ID: worker-docker-1
    volumes:
      - ./storage:/app/storage
      - ./models:/app/models:ro
    depends_on:
      db:
        condition: service_healthy
    networks:
      - safevision-net

  frontend:
    build:
      context: ./frontend
      args:
        VITE_API_BASE_URL: ${VITE_API_BASE_URL}
        VITE_ENABLE_AUTH: ${VITE_ENABLE_AUTH}
    ports:
      - "5173:80"
    depends_on:
      - backend
    networks:
      - safevision-net

volumes:
  pgdata:

networks:
  safevision-net:
    driver: bridge
ترتيب البدء

depends_on مع condition: service_healthy يجعل Compose ينتظر حتى تجيب PostgreSQL على فحص pg_isready قبل تشغيل الـ backend. هذا يمنع أشهر خطأ في النشر المحلي: بدء الـ API قبل جهوزية قاعدة البيانات.

19.11 الخطوات السبع للتشغيل

  1. Build (البناء): نبني صور الـ backend والـ frontend من الـ Dockerfiles.
  2. Up (التشغيل): نرفع الحاويات الأربع مع الشبكة والـ volumes.
  3. Logs (السجلات): نتابع مخرجات كل خدمة لاكتشاف أخطاء البدء.
  4. Migrate (الترحيل): ننفّذ ترحيلات Alembic داخل حاوية الـ backend لإنشاء الجداول.
  5. Health (الفحص): نتأكد من GET /api/v1/health ومن فتح الواجهة.
  6. Restart (إعادة التشغيل): نعيد خدمة واحدة بعد تعديل الكود دون إسقاط الباقي.
  7. Data persistence (دوام البيانات): نتأكد أن الفيديوهات والوقائع باقية بعد إعادة التشغيل.
terminal — run the full stackbash
# 1) Build images from the two Dockerfiles
$ docker compose build

# 2) Start db + backend + worker + frontend
$ docker compose up -d

# 3) Follow logs (Ctrl+C stops following, not the containers)
$ docker compose logs -f backend worker

# 4) Create the database schema with Alembic
$ docker compose exec backend alembic upgrade head

# 5) Health check and open the UI
$ curl http://localhost:8000/api/v1/health
$ start http://localhost:5173

# 6) Restart one service after a code change
$ docker compose restart backend

# 7) Verify data persistence
$ docker compose down
$ docker compose up -d
$ curl http://localhost:8000/api/v1/videos

19.13 حدود دعم GPU في Docker وبديل CPU

تشغيل PyTorch على GPU داخل Docker يحتاج تعريف الحاوية ببطاقة الرسوميات. على Linux يمكن ذلك عبر NVIDIA Container Toolkit وإضافة قسم deploy.resources في Compose. أمّا على Windows فيعتمد الأمر على إصدار Docker Desktop ووجود WSL2 ودعم البطاقة، وقد لا يتوفّر أصلاً على أجهزة الـ GPU المدمجة. لذلك نتبنّى قاعدة عملية واضحة:

  • وضع GPU: يضاف قسم الموارد، ويُضبط MODEL_DEVICE=cuda. يُستخدم على جهاز الفريق الذي يملك بطاقة متوافقة عند الحاجة إلى سرعة أعلى.
  • وضع CPU (الافتراضي للعرض): يبقى MODEL_DEVICE=cpu، ويعمل النظام كاملاً بدون أي بطاقة. أبطأ، لكنه يعمل على أي جهاز ولجنة المناقشة.
حدود GPU غير مضمونة

لا نضمن توفر GPU على جهاز العرض أو على أي استضافة. الأرقام المتعلقة بالسرعة تُقاس على الجهاز المستخدم فعلاً وتُوثَّق في الفصل 23، ولا نفترض أن الحاوية سترى البطاقة تلقائياً. إن فشل تشغيل CUDA فالحل الآمن هو العودة إلى MODEL_DEVICE=cpu، وهذا هو وضع العرض الافتراضي في الفصل 28.

docker-compose.override.yml — optional GPU block (Linux + NVIDIA)yaml
# Optional file. Only use it on a machine that really exposes a GPU.
services:
  worker:
    environment:
      MODEL_DEVICE: cuda
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
خلاصة الفصل 19

ما تعلّمناه

غلافنا النظام في أربع حاويات (db، backend، worker، frontend) على شبكة واحدة، وفهمنا أن الحاويات تتحدّث بأسماء الخدمات لا بـ localhost، وأن البيانات الدائمة تعيش في الـ volumes. وثبّتنا وضع CPU كافتراضي ووضع GPU كخيار مشروط.

ما يجب تنفيذه

  • كتابة backend/Dockerfile وfrontend/Dockerfile.
  • كتابة .dockerignore وdocker-compose.yml.
  • ضبط DATABASE_URL لاستخدام اسم الخدمة db.
  • تجهيز مجلد ./models بملفات الـ checkpoints قبل البناء.

المخرجات المتوقعة

  • أمر واحد docker compose up -d يشغّل النظام كاملاً.
  • واجهة على localhost:5173 و API على localhost:8000.
  • بيانات باقية بعد docker compose down ثم up.

كيف نتحقق من الإنجاز

  • GET /api/v1/health يعيد 200 بعد التشغيل النظيف.
  • الـ worker يلتقط job ويحدّث التقدّم داخل الحاوية.
  • رفع فيديو من الواجهة ينجح ويظهر في قائمة /api/v1/videos.

أخطاء شائعة

  • استخدام localhost في DATABASE_URL داخل الحاويات.
  • نسيان ربط مجلد الـ models فتظهر رسالة "checkpoint not found".
  • افتراض أن GPU سيعمل تلقائياً على Windows.
  • تشغيل down -v على بيانات حقيقية.

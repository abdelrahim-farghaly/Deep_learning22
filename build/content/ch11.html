خط معالجة الفيديو والـ Background Jobs

لماذا لا نعالج فيديو طويلاً داخل طلب HTTP واحد، وكيف نبني worker مستقلاً

معالجة فيديو دقائق قد تستغرق وقتاً أطول بكثير من مهلة أي طلب HTTP. لهذا نفصل الطلب عن التنفيذ: الـ API ينشئ وظيفة (job) ويعيد فوراً، وعملية مستقلة تُسمّى worker تلتقط الوظائف وتنفّذها وتُحدّث التقدّم في قاعدة البيانات.

11.1 لماذا الطلب المتزامن خطأ

لو عالجنا الفيديو داخل POST /api/v1/videos/{video_id}/process مباشرةً، لانتظر المتصفح دقائق حتى ينتهي الطلب، ثم قد يقطعه انقطاع الشبكة أو إعادة تحميل الصفحة، فتضيع كل النتيجة. كما أن خادم Uvicorn محدود بعدد العمليات، وقد يتجمّد عند معالجة عدّة فيديوهات معاً. الحل: تنفيذ طويل ومنفصل، وواجهة تستعلم عن الحالة.

11.2 تصميم خط الـ Jobs في ست عشرة خطوة

  1. وصول طلب POST /api/v1/videos/{video_id}/process.
  2. التحقق من وجود الفيديو وأن حالته تسمح بالمعالجة.
  3. إنشاء صف في processing_jobs بحالة queued.
  4. إرجاع 202 مع كائن JobOut فوراً.
  5. الـ worker يستعلم دورياً عن وظيفة queued.
  6. حجز الوظيفة (claim) وتحويلها إلى running.
  7. فتح ملف الفيديو وقراءة عدد الإطارات والمدة و fps.
  8. تحميل الـ Models مرة واحدة عبر السجل (الفصل 10).
  9. المرور على الإطارات مع frame sampling.
  10. تشغيل الـ inference على الإطارات المختارة فقط.
  11. تطبيع المخرجات إلى كائنات Detection.
  12. تقييم قواعد السلامة (SafetyRuleEngine).
  13. توليد الوقائع وحفظ صور الدليل.
  14. تحديث progress و frames_processed دورياً.
  15. إغلاق الوظيفة completed وتحديث حالة الفيديو إلى processed.
  16. عند الفشل: failed مع error_message واضح.

11.3 حالات الـ Job

الحالة تتبع القيم الخمس في المواصفة: queued ثم running ثم completed أو failed، ويمكن cancelled قبل البدء. لا نخرج عن هذه القيم أبداً.

11.4 لماذا لا نستخدم BackgroundTasks كنظام jobs

يوفّر FastAPI آلية BackgroundTasks لتنفيذ عمل بعد إرجاع الردّ، لكنها ليست نظام وظائف موثوقاً للأسباب التالية:

  • تعيش داخل عملية الخادم: إذا أُعيد تشغيل الـ API أو تعطّل، تضيع المهمة بلا أثر.
  • لا يوجد صف دائم: لا يوجد سجل يمكن الاستعلام عنه لمعرفة الحالة أو التقدّم.
  • لا إعادة محاولة: لا توجد retries ولا استئناف بعد الفشل.
  • تنافس على الموارد: تعمل داخل نفس عملية الـ API فتنافس الطلبات على الـ CPU/GPU.
  • لا قابلية للتوسّع: لا يمكن تشغيل عدّة عمّال على أجهزة مختلفة.
القاعدة

نستخدم BackgroundTasks لمهام صغيرة غير حرجة فقط (مثل كتابة سجل)، أما المعالجة الثقيلة فمكانها الـ worker المستقل.

11.5 الـ Worker المستقل وقائمة الوظائف المبنية على قاعدة البيانات

نستخدم طابور وظائف مدعوماً بقاعدة البيانات (DB-backed queue): الوظائف صفوف في processing_jobs، والـ worker عملية منفصلة تستعلم عنها. الحجز يتم بـ SELECT ... FOR UPDATE SKIP LOCKED حتى لا يلتقط عاملان نفس الوظيفة. هذا يحقّق الموثوقية بلا إدخال Redis أو Celery (المستبعدين من الـ MVP).

11.6 Frame sampling كمعامل قابل للضبط

لا نحلّل كل إطار؛ نختار إطاراً كل FRAME_SAMPLE_EVERY_N إطار (الافتراضي 5). يوفّر هذا وقتاً كبيراً، لكنه قد يُفوّت حدثاً قصيراً. لذلك نضبط القيمة بعد التحقق من ثلاثة أمور: معدّل استرجاع الأحداث (event recall)، ومدة الفيديو، وسرعة المعالجة على العتاد المتاح. ونضع حدّاً أعلى للإطارات عبر MAX_FRAMES_PER_JOB.

كيف نختار N؟

ابدأ بـ 5 على فيديو عرض قصير، وقِس زمن المعالجة، ثم كبّر الرقم إذا كان الوقت طويلاً جداً، أو صغّره إذا لاحظنا أحداثاً مفقودة.

11.7 منع المعالجة المزدوجة ونفاد الموارد

  • على مستوى قاعدة البيانات: الفهرس الفريد الجزئي يمنع وظيفتين نشطتين لنفس الفيديو.
  • على مستوى الحجز: SKIP LOCKED يمنع عاملين من أخذ نفس الوظيفة.
  • على مستوى الموارد: الـ checkpoint يُحمَّل مرة واحدة، وWORKER_CONCURRENCY يحدّد عدد الوظائف المتزامنة في العامل، فنمنع تشغيل عدّة inference ثقيلة معاً.
  • عند الفشل: نُعيد الوظيفة أو نعلّمها failed حسب JOB_MAX_RETRIES، مع تنظيف أي دليل ناقص.

11.8 نسبة التقدّم ورسائل الخطأ

نحسب progress كنسبة مئوية بين frames_processed و frames_total، ونحدّثه دورياً (لا في كل إطار) لتقليل الكتابة. الواجهة تستعلم عبر GET /api/v1/jobs/{job_id} وتعرض الشريط. عند الفشل نكتب سبباً واضحاً في error_message بدل رسالة غامضة.

backend/app/services/job_service.pypython
# backend/app/services/job_service.py
import uuid
from sqlalchemy import select
from sqlalchemy.orm import Session
from app.core.config import settings
from app.models.enums import JobStatus, VideoStatus
from app.models.processing_job import ProcessingJob
from app.models.video import Video


class JobService:
    """Create and claim processing jobs (DB-backed queue)."""

    def __init__(self, db: Session) -> None:
        self.db = db

    def create_for_video(self, video_id: uuid.UUID) -> ProcessingJob:
        video = self.db.get(Video, video_id)
        if video is None:
            raise ValueError("video not found")
        job = ProcessingJob(video_id=video.id, status=JobStatus.queued,
                             sample_every_n_frames=settings.FRAME_SAMPLE_EVERY_N)
        video.status = VideoStatus.processing
        self.db.add(job)
        self.db.commit()
        self.db.refresh(job)
        return job

    def claim_next(self, worker_id: str) -> ProcessingJob | None:
        stmt = (select(ProcessingJob)
                .where(ProcessingJob.status == JobStatus.queued)
                .order_by(ProcessingJob.created_at)
                .with_for_update(skip_locked=True)
                .limit(1))
        job = self.db.execute(stmt).scalar_one_or_none()
        if job is None:
            return None
        job.status = JobStatus.running
        job.worker_id = worker_id
        self.db.commit()
        return job
backend/app/workers/processor.pypython
# backend/app/workers/processor.py
from pathlib import Path
import cv2
from sqlalchemy.orm import Session
from app.ai.model_registry import (
    get_ppe_detector, get_fire_smoke_detector, get_person_tracker)
from app.ai.rules import SafetyRuleEngine
from app.core.config import settings
from app.models.enums import JobStatus, VideoStatus
from app.services.incident_service import IncidentService


class VideoProcessor:
    """Runs the pipeline for a single job."""

    def __init__(self, db: Session) -> None:
        self.db = db
        self.rules = SafetyRuleEngine()

    def process(self, job) -> None:
        path = str(Path(settings.LOCAL_STORAGE_ROOT) / job.video.storage_key)
        capture = cv2.VideoCapture(path)
        frame_number = 0
        while True:
            ok, frame = capture.read()
            if not ok:
                break
            if frame_number % job.sample_every_n_frames == 0:
                timestamp = frame_number / (job.video.fps or 25.0)
                detections = self._infer(frame, frame_number, timestamp)
                for incident in self.rules.evaluate(detections):
                    IncidentService(self.db).persist(job, incident, frame)
                self._progress(job, frame_number)
            frame_number += 1
        capture.release()
        job.status = JobStatus.completed
        job.video.status = VideoStatus.processed
        self.db.commit()

    def _infer(self, frame, frame_number, timestamp) -> list:
        out = []
        out += get_ppe_detector().predict(frame, frame_number, timestamp)
        out += get_fire_smoke_detector().predict(frame, frame_number, timestamp)
        out += get_person_tracker().predict(frame, frame_number, timestamp)
        return out

    def _progress(self, job, frame_number: int) -> None:
        if job.frames_total:
            job.frames_processed = frame_number
            job.progress = round(100 * frame_number / job.frames_total, 2)
            self.db.commit()
backend/app/workers/run_worker.pypython
# backend/app/workers/run_worker.py
import time
import uuid
from app.core.config import settings
from app.db.session import SessionLocal
from app.models.enums import JobStatus
from app.services.job_service import JobService
from app.workers.processor import VideoProcessor

WORKER_ID = settings.WORKER_ID or f"worker-{uuid.uuid4().hex[:8]}"


def run_forever() -> None:
    while True:
        with SessionLocal() as db:
            job = JobService(db).claim_next(WORKER_ID)
            if job is None:
                time.sleep(settings.WORKER_POLL_INTERVAL_SECONDS)
                continue
            try:
                VideoProcessor(db).process(job)
            except Exception as exc:  # one job must not kill the worker
                job.status = JobStatus.failed
                job.error_message = str(exc)
                db.commit()


if __name__ == "__main__":
    run_forever()

في نافذة طرفية منفصلة: python -m app.workers.run_worker، ويمكن تشغيل أكثر من نسخة على أجهزة مختلفة لأن الحجز عبر قاعدة البيانات آمن.

11.11 متى نحتاج Task Queue فعلاً؟

طابور قاعدة البيانات كافٍ لفريق طلابي وعدد محدود من العمّال على جهاز واحد. نحتاج نظاماً مثل Redis أو Celery فقط عند تشغيل عمّال على عدّة أجهزة، أو الحاجة إلى جدولة مؤقتة وأولويات معقّدة ومهام متكرّرة. كل هذا خارج نطاق الـ MVP، وذكره هنا ليعرف الفريق حدّ التصميم الحالي.

أما إلغاء الوظيفة cancelled فيتاح فقط قبل بدء التنفيذ؛ فبعد أن يلتقط الـ worker الوظيفة نتركه يُنهي الإطار الحالي بأمان بدل قتل العملية فجأة.

خلاصة الفصل 11

ما تعلّمناه

لماذا نفصل التنفيذ عن الطلب، وكيف نبني طابور وظائف على قاعدة البيانات، ولماذا BackgroundTasks غير كافٍ، وكيف نمنع المعالجة المزدوجة ونضبط frame sampling.

ما يجب تنفيذه

  • كتابة job_service.py و processor.py و run_worker.py.
  • تنفيذ POST /api/v1/videos/{video_id}/process و GET /api/v1/jobs/{job_id}.
  • ضبط FRAME_SAMPLE_EVERY_N و WORKER_POLL_INTERVAL_SECONDS.

المخرجات المتوقعة

  • وظيفة تُنشأ وتُلتقط وتُكمل مع تحديث التقدّم.
  • خطأ في وظيفة لا يوقف الـ worker ولا بقية الوظائف.

كيف نتحقق من الإنجاز

  • إيقاف الـ API أثناء تشغيل وظيفة لا يضيّعها لأنها في قاعدة البيانات.
  • محاولة إنشاء وظيفتين لنفس الفيديو تُرفض.
  • إيقاف الـ worker ثم تشغيله يستأنف التقاط الوظائف المعلّقة.

أخطاء شائعة

  • الاعتماد على BackgroundTasks لمعالجة ثقيلة.
  • تحديث التقدّم في كل إطار فيُبطئ المعالجة.
  • تشغيل عدّة عمّال ثقيلة على نفس الجهاز فتتضارب الموارد.
  • عدم التقاط الأخطاء فيتوقّف الـ worker عند أول فيديو تالف.

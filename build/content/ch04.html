هيكل المستودع وتنظيم المجلدات

أين يوضع كل ملف، وما لا يجب أن يدخل Git أبداً

نثبّت هنا شجرة المجلدات كاملة، ووظيفة كل مجلد، وما يُرفع إلى GitHub وما لا يُرفع أبداً، مع ملفَّي .gitignore و.env.example جاهزين للنسخ.

هذه الشجرة هي المرجع الرسمي؛ كل ملف جديد يجب أن يجد مكانه فيها، ولا ننشئ مجلدات عشوائية.

4.3 ما لا يجب أن يدخل Git أبداً ولماذا

Git: نظام تتبّع الإصدارات، وهو مصمَّم للنصوص الصغيرة لا للملفات الضخمة، لذلك ثلاثة أصناف لا نرفعها:

  • الملفات الكبيرة (Binaries): الفيديوهات وأوزان الـ Models؛ رفعها يُنتفخ حجم المستودع ويجعل كل git clone بطيئاً.
  • البيانات المولَّدة (Generated): صور الدليل والتقارير؛ مخرجات تشغيل يمكن إعادة توليدها.
  • الأسرار (Secrets): كلمة مرور قاعدة البيانات وSECRET_KEY ومفاتيح S3؛ تسريبها خطر أمني حقيقي.
خطر

رفع ملف .env أو أي مفتاح حقيقي خطأ لا يُصلَح بمجرد الحذف لأن التاريخ يحتفظ به. نرفع .env.example فقط وننشئ .env محلياً.

خلاصة الفصل 4

ما تعلّمناه

ثبّتنا شجرة المجلدات الرسمية، ووظيفة كل مجلد، وأصناف الملفات الثلاثة التي لا تدخل Git (الملفات الكبيرة، والمخرجات المولَّدة، والأسرار)، وكتبنا .gitignore و .env.example كاملين، واتفقنا على قواعد التسمية والفروع.

ما يجب تنفيذه

  • إنشاء المستودع وشجرة المجلدات كما في القسم 4.1.
  • إضافة .gitignore و.env.example قبل أول commit.
  • نسخ .env.example إلى .env على كل جهاز وملء القيم.
  • الاتفاق على حماية الفرع main من الدفع المباشر.

المخرجات المتوقعة

  • مستودع GitHub نظيف يحتوي الكود فقط بلا ملفات كبيرة.
  • ملف README.md يشرح خطوات التشغيل.
  • قالب بيئة موحّد لكل الأعضاء.

كيف نتحقق من الإنجاز

  • الأمر git status لا يُظهر أي ملف في storage/ أو models/.
  • حجم المستودع بعد git clone صغير (ميجابايتات قليلة).
  • لا يوجد ملف .env أو مفتاح حقيقي في تاريخ المستودع.

أخطاء شائعة

  • رفع ملف .env الحقيقي بالخطأ.
  • رفع أوزان الـ Models فيصبح الاستنساخ بطيئاً جداً.
  • إنشاء مجلدات بأسماء عشوائية خارج الشجرة المعتمدة.
  • الدفع المباشر إلى main دون مراجعة.

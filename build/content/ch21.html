CH21 · CI/CD

الـ CI/CD وسير عمل GitHub

كيف يعمل خمسة طلاب على مستودع واحد دون فوضى

أكبر خطر في مشروع فريق هو فقدان العمل أو دمج كود يكسر ما بناه غيرك. هذا الفصل يثبّت قواعد عمل بسيطة على مستودع safevision-ai، ثم يعرض ملف CI اختيارياً يفحص الكود تلقائياً عند كل تغيير. القاعدة الحاكمة: لا أحد يعمل مباشرة على الفرع main.

21.1 نموذج الفروع الذي نستخدمه

Branch (فرع): نسخة مستقلة من الكود يمكن التعديل عليها دون التأثير على الفرع الرئيسي. نستخدم نموذجاً بسيطاً يكفي خمسة أعضاء: فرع main يمثّل النسخة المستقرّة دائماً، وفرع مؤقت لكل مهمة يُنشأ منه ثم يُدمج فيه عبر Pull Request.

جدول 21-1: قواعد التسمية
النوعالصيغةأمثلة
فرع ميزةfeat/<short-name>feat/video-upload, feat/incident-list
إصلاح خطأfix/<short-name>fix/cors-origins, fix/job-progress
توثيقdocs/<short-name>docs/api-contract
الوسومv<major>.<minor>.<patch>v0.1.0, v1.0.0

21.2 Pull Requests ومراجعة الكود

Pull Request (PR): طلب دمج فرعك في main مع عرض التغييرات للنقاش. لا يُدمج أي PR قبل مراجعة عضو آخر على الأقل. نُبقي الـ PR صغيراً: مهمة واحدة، تغيير محدود، وصف واضح لما تغيّر وكيف اختُبر. هذا يجعل المراجعة سريعة ويمنع تعارضات الدمج الكبيرة.

PR جيّد
  • مهمة واحدة فقط ورسالة واضحة.
  • يربط بـ Issue برقمه.
  • يشرح كيف اختُبر يدوياً.
  • صغير بما يكفي لمراجعته في دقائق.
PR سيّئ
  • يخلط بين ميزات متعددة.
  • يحتوي ملفات كبيرة أو أسراراً بالخطأ.
  • بدون وصف ولا خطوات اختبار.
  • يبقى مفتوحاً أسابيع فيتعارض مع غيره.

21.3 حل تعارضات الدمج ورسائل الـ Commit

يحدث Merge Conflict عندما يعدّل فرعان نفس الأسطر. الحل دائماً: اسحب أحدث نسخة من main إلى فرعك مبكراً، ثم حلّ التعارض يدوياً واختبار الكود قبل الدمج. أما رسائل الـ commit فنتبع صيغة مختصرة type(scope): message بالإنجليزية.

terminal — daily Git workflowbash
# Start a task from an up-to-date main
$ git checkout main
$ git pull origin main
$ git checkout -b feat/video-upload

# Work, then stage and commit in small logical steps
$ git add backend/app/api/v1/videos.py
$ git commit -m "feat(videos): add multipart upload endpoint"

# Pull main into your branch early to resolve conflicts while they are small
$ git fetch origin
$ git rebase origin/main

# Push and open a Pull Request
$ git push -u origin feat/video-upload

# After the PR is reviewed and merged, clean up the branch
$ git checkout main
$ git pull origin main
$ git branch -d feat/video-upload
قاعدة الدمج المبكر

كلما طال بقاء الفرع منفصلاً كبرت التعارضات. القاعدة: اسحب أحدث نسخة من main إلى فرعك مرة كل يوم عمل على الأقل، ولا تُبقِ فرعاً بدون دمج أكثر من بضعة أيام. وإن كبر التعارض، فالحل ليس إجبار الدمج (push --force) على فرع مشترك، بل حلّ التعارض ملفاً ملفاً واختبار الكود بعد الحل.

21.4 Issues و Milestones و Release Tags

نستخدم Issues لتسجيل كل مهمة أو خطأ، وMilestones لتجميع الإصدارات في مجموعات قابلة للقياس (مثل: الأساس، خط المعالجة، الواجهة، العرض النهائي). وكلما وصل النظام إلى حالة مستقرة نضع وسم إصدار Tag بالإنجليزية. هذا يعطي الفريق خط أساس يعود إليه عند كسر شيء.

ويُفضّل أن يحمل كل Issue قائمة تحقق صغيرة (definition of done) تُغلق المهمة فقط عند إتمامها، وأن يُربط اسم الفرع برقم الـ Issue ليعرف المراجع سياق التغيير فوراً.

21.5 GitHub Actions اختياري

GitHub Actions: خدمة تشغيل أوامر تلقائياً عند كل push أو PR. الـ CI مفيد فعلاً بعد أن يصبح لدينا اختبارات قابلة للتشغيل. الملف التالي يفحص صياغة Python، ويشغّل الاختبارات، ويبني الواجهة ويفحص الأنواع، ويبني صورة Docker للـ backend. نستخدم services لتوفير PostgreSQL مؤقتة للاختبارات، ونأخذ الأسرار من secrets لا من الكود.

.github/workflows/ci.ymlyaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: safevision
          POSTGRES_PASSWORD: safevision
          POSTGRES_DB: safevision_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U safevision"
          --health-interval 10s --health-timeout 5s --health-retries 5
    env:
      DATABASE_URL: postgresql+psycopg://safevision:safevision@localhost:5432/safevision_test
      MODEL_DEVICE: cpu
      AUTH_ENABLED: "false"
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r backend/requirements.txt
      - run: ruff check backend
      - run: pytest backend/tests -q

  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - run: npm ci
      - run: npm run lint
      - run: npm run build
      - run: npx tsc --noEmit

  docker:
    runs-on: ubuntu-latest
    needs: backend
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t safevision-backend ./backend
تحذير أمني صريح

لا تُرفع إلى GitHub أبداً: فيديوهات العملاء أو أي فيديو حقيقي، ملفات الـ checkpoints الضخمة (models/)، ملف .env الذي يحوي كلمات مرور، أو أي مفتاح S3_SECRET_ACCESS_KEY. كل هذه مستثناة في .gitignore وفي .dockerignore. إن رُفع سرّ بالخطأ فالحل ليس حذف الملف في commit جديد، بل إلغاء السرّ فوراً من المصدر لأنه يبقى في تاريخ Git.

21.6 متى يصبح الـ CI/CD مفيداً فعلاً

الـ CI ليس هدفاً في ذاته، بل أداة. يصبح مفيداً عندما تتحقق ثلاثة شروط: أن توجد اختبارات يمكن تشغيلها آلياً، وأن يكون الكود على فرع main صالحاً للتشغيل دائماً، وأن يستطيع عضو جديد تشغيل المشروع من التعليمات وحدها. قبل ذلك يتحوّل الـ CI إلى عمل زائد يستهلك وقت الفريق.

لذلك الترتيب الصحيح: نكتب الكود والاختبارات أولاً، ونضبط .gitignore، ثم نضيف ملف الـ workflow. البوابة الأولى (gate) هي تشغيل pytest وnpm run build محلياً قبل الـ push، لأن تشغيل الأمر على جهازك أسرع بكثير من انتظار CI. أمّا CI فقيمته الحقيقية أنه يمنع دمج كود يكسر فرع main دون أن يلاحظه أحد.

نقطة أخيرة: لا نعتمد على CI لتشغيل الـ AI على GPU. الاختبارات في CI تعمل على CPU وبفيديو صناعي صغير جداً (الفصل 22)، وأي شيء يحتاج GPU أو بيانات حقيقية يبقى اختباراً يدوياً موثّقاً. هكذا تبقى بوابة CI سريعة وغير مكلفة، ولا تفشل بسبب موارد غير متوفرة.

خلاصة الفصل 21

ما تعلّمناه

ثبّتنا نموذج فروع بسيطاً: main مستقر دائماً، وفرع لكل مهمة، ودمج عبر Pull Request بمراجعة. واتفقنا على صيغة رسائل الـ commit، وعلى Issues وMilestones وTags، وعلى ملف CI اختياري يفحص الـ backend والـ frontend ويبني الصورة.

ما يجب تنفيذه

  • تفعيل حماية فرع main ومنع الدفع المباشر.
  • إنشاء قالب للـ Pull Request يطلب وصف التغيير وخطوات الاختبار.
  • التحقق من .gitignore قبل أول commit.
  • إضافة .github/workflows/ci.yml عند جاهزية الاختبارات.

المخرجات المتوقعة

  • مستودع فيه فرع main نظيف ووسوم إصدار.
  • لوحة Issues وMilestones تغطّي كل مهام الفصل 26.
  • تشغيل CI أخضر على آخر PR.

كيف نتحقق من الإنجاز

  • لا يمكن الدفع مباشرة إلى main.
  • كل PR له مراجع واحد على الأقل ووصف واضح.
  • لا يوجد ملف سرّ أو فيديو داخل المستودع.

أخطاء شائعة

  • العمل مباشرة على main من عدة أعضاء.
  • ترك فروع مفتوحة طويلاً حتى تكبر التعارضات.
  • رفع ملف .env أو مجلد models/ بالخطأ.
  • توقّع أن CI يصلح الكود بدل أن يكتشف الأخطاء فقط.

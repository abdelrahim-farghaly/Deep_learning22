الاختبارات وضمان الجودة

كيف نتأكد أن النظام يعمل فعلاً قبل المناقشة

هذا الفصل يحوّل الثقة إلى دليل: اختبارات وحدات، وتكامل بين الـ API وقاعدة البيانات، ورحلة كاملة من الطرف للطرف، وجدول حالات اختبار تُملأ خاناته بعد التنفيذ. القاعدة: لا نكتب نتيجة لم تُنفَّذ.

22.1 ثلاثة مستويات من الاختبار

جدول 22-1: مستويات الاختبار الثلاثة ونطاق كل واحد
المستوىما يختبرهأدواتسرعة
Unit Testingدالة واحدة معزولة: فلترة الثقة، تقييم قاعدة، حساب تقريرpytestأجزاء من الثانية
Integration Testingعدة مكوّنات معاً: API + قاعدة بيانات، Job + AI، وقائع + تقاريرpytest + httpxثوانٍ
End-to-End Testingرحلة المستخدم الكاملة من الرفع حتى التقريرتشغيل كامل + المتصفحدقائق

Unit Test (اختبار وحدة): يفحص أصغر قطعة منطق بمعزل، بلا قاعدة بيانات أو GPU أو شبكة. وIntegration Test (اختبار تكامل): يفحص أن قطعتين تعملان معاً، مثل رفع الـ API فيديو فيظهر في جدول videos.

22.2 اختبارات الوحدة: ماذا نغطّي بالضبط

  • التحقق من الفيديو: امتداد مسموح/مرفوض، تجاوز MAX_UPLOAD_MB، ملف تالف.
  • خريطة الأصناف: اسم class من الـ Model إلى نوع واقعة صحيح.
  • فلترة الثقة: كشف أقل من DETECTION_CONF_THRESHOLD يُستبعد.
  • تقييم القواعد: مخالفة PPE تتطلب إطارات متتالية، والدخان عتبة أعلى.
  • منع تكرار الوقائع: واقعة داخل INCIDENT_COOLDOWN_SECONDS لا تُنشأ مرتين.
  • حسابات التقارير: تجميع الوقائع يومياً يعطي نفس المجموع.

22.3 اختبارات التكامل: نقاط الوصل الحرجة

نركّز على وصلات الخطأ الشائعة: API مع قاعدة البيانات، الرفع مع التخزين، Job مع AI، مخرجات الـ AI مع الوقائع، الوقائع مع التقارير، وFrontend مع Backend. في كل اختبار نتحقق من رمز الحالة (201، 202، 200) ومن شكل الاستجابة المطابق للعقد ومن وصول البيانات للجدول الصحيح.

22.4 اختبار الرحلة الكاملة (End-to-End)

  1. فتح الواجهة والتأكد من نجاح نداء GET /api/v1/health.
  2. رفع فيديو صغير عبر POST /api/v1/videos وظهوره في القائمة.
  3. بدء المعالجة POST /api/v1/videos/{video_id}/process والحصول على 202.
  4. متابعة GET /api/v1/jobs/{job_id} حتى completed.
  5. ظهور وقائع في GET /api/v1/incidents.
  6. فتح تفاصيل واقعة وعرض صورة الدليل عبر /api/v1/evidence/{evidence_id}/file.
  7. تنفيذ مراجعة PATCH /api/v1/incidents/{incident_id} وتغيّر الحالة.
  8. فتح التحليلات GET /api/v1/analytics/overview وظهور الأرقام.
  9. تصدير التقرير GET /api/v1/reports/export وفتح ملف CSV.
  10. حذف الفيديو والتأكد من اختفاء وقائعه وملفاته.

22.6 الاختبار بدون GPU وفيديو صناعي صغير

الاختبارات الآلية يجب ألا تحتاج GPU ولا فيديو حقيقي. ننشئ fixture — بيانات ثابتة تُجهَّز تلقائياً — على شكل فيديو صناعي صغير جداً نولّده بإطارات ملوّنة، ونضبط MODEL_DEVICE=cpu وAUTH_ENABLED=false، ونستبدل الـ Model الثقيل بـ stub يعيد كشوفات ثابتة.

22.7 ملف الـ fixtures

يجهّز هذا الملف بيانات الاختبار المشتركة: فيديو صناعي صغير، وعميل HTTP، وجلسة قاعدة بيانات تُلغى في النهاية.

22.8 اختبار قواعد السلامة

نختبر تقييم القواعد بكشوفات مصنوعة يدوياً بلا Model أو GPU: مخالفة PPE أقل من الإطارات المطلوبة لا تُنتج واقعة، وواقعة داخل فترة التهدئة لا تُكرَّر.

backend/tests/test_rules.pypython
from app.ai.rules import evaluate_ppe_violation, should_create_incident


def make_detection(frame_number, class_name="person_no_helmet", confidence=0.9):
    return {
        "class_name": class_name,
        "confidence": confidence,
        "bbox": [10, 10, 50, 50],
        "frame_number": frame_number,
        "timestamp_seconds": frame_number / 5.0,
    }


def test_single_frame_below_confirm_threshold_makes_no_incident():
    # INCIDENT_CONFIRM_FRAMES is higher than one, so a single frame is not enough.
    detections = [make_detection(1)]
    assert evaluate_ppe_violation(detections, confirm_frames=3) is None


def test_repeated_frames_produce_one_incident():
    detections = [make_detection(n) for n in range(1, 6)]
    incident = evaluate_ppe_violation(detections, confirm_frames=3)
    assert incident is not None
    assert incident["incident_type"] == "ppe_violation"
    assert incident["detection_count"] >= 3


def test_cooldown_blocks_duplicate_incident():
    last_seen_seconds = 4.0
    new_detection_seconds = 6.0
    assert should_create_incident(
        last_seen_seconds, new_detection_seconds, cooldown_seconds=10.0
    ) is False

يمرّ هذا الاختبار عبر الـ API الحقيقي ويتحقق من رمز الحالة وشكل الاستجابة وتغيّر الحالة. نستخدم TestClient أو httpx.AsyncClient للـ endpoints غير المتزامنة.

def test_list_incidents_returns_pagination_envelope(client):
    response = client.get("/api/v1/incidents")
    assert response.status_code == 200
    body = response.json()
    # The pagination envelope is defined in the API contract.
    for key in ("items", "total", "page", "page_size", "pages"):
        assert key in body


def test_incident_status_change_is_recorded(client):
    # Assumes a seeded incident exists in the test database.
    incident_id = client.get("/api/v1/incidents").json()["items"][0]["id"]
    response = client.patch(
        f"/api/v1/incidents/{incident_id}",
        json={"status": "confirmed", "note": "checked by reviewer"},
    )
    assert response.status_code == 200
    assert response.json()["status"] == "confirmed"


def test_reject_invalid_status_value(client):
    incident_id = client.get("/api/v1/incidents").json()["items"][0]["id"]
    response = client.patch(
        f"/api/v1/incidents/{incident_id}", json={"status": "not_a_real_status"}
    )
    assert response.status_code == 422

22.10 اختبار الواجهة بـ Vitest

على الـ Frontend نستخدم Vitest لاختبار الدوال النقية: تنسيق الأرقام، والتحقق من الامتداد قبل الرفع، وتحويل قيم الـ enums إلى نصوص للعرض.

frontend/src/utils/format.test.tstypescript
import { describe, expect, it } from "vitest";
import { formatProgress, isAllowedVideo } from "./format";

describe("isAllowedVideo", () => {
  it("accepts mp4 and rejects txt", () => {
    expect(isAllowedVideo("clip.mp4")).toBe(true);
    expect(isAllowedVideo("notes.txt")).toBe(false);
  });
});

describe("formatProgress", () => {
  it("rounds a fraction to a percentage string", () => {
    expect(formatProgress(0.425)).toBe("43%");
  });
});

خلاصة الفصل 22

ما تعلّمناه

قسّمنا الاختبارات إلى وحدة وتكامل ورحلة كاملة، وجهّزنا فيديو صناعياً يعمل بدون GPU، وربطنا كل اختبار برمز الحالة وشكل الاستجابة في العقد.

ما يجب تنفيذه

  • كتابة backend/tests/conftest.py بالـ fixtures.
  • كتابة اختبارات القواعد والـ API وتشغيلها محلياً.
  • تعبئة جدول حالات الاختبار بعد تنفيذ فعلي.
  • إضافة Vitest لاختبار دوال الواجهة.

المخرجات المتوقعة

  • حزمة اختبارات تعمل بالكامل على CPU.
  • جدول حالات اختبار مكتمل بالنتائج الحقيقية.
  • تقرير مختصر بعدد الاختبارات الناجحة والفاشلة.

كيف نتحقق من الإنجاز

  • تشغيل pytest دون أخطاء جمع أو فشل غير متوقع.
  • كل صف في جدول الحالات له نتيجة مكتوبة وسبب.
  • إمكانية تشغيل الاختبارات على جهاز بلا GPU.

أخطاء شائعة

  • كتابة Expected في خانة Actual لمجرد أن الاختبار "يجب" أن ينجح.
  • الاعتماد على بيانات حقيقية في الاختبارات الآلية.
  • اختبارات تعتمد على ترتيب التنفيذ أو تترك بيانات في قاعدة البيانات.
  • نسيان تشغيل الاختبارات قبل كل push.

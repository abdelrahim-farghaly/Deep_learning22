CH07 · API CONTRACT

تصميم الـ API وتوثيق الـ Endpoints

عقد واحد يتفق عليه الـ Backend والـ Frontend قبل كتابة الكود

عقد الـ API (API contract) هو الاتفاق الملزم بين الـ Backend والـ Frontend: أسماء المسارات، وأشكال الطلب والرد، ورموز الحالة، وأشكال الخطأ. تثبيته أولاً يسمح ببناء الطرفين بالتوازي، وهو المرجع الحرفي لكل نداء في الفصول التالية.

7.1 لماذا نكتب العقد أولاً

البناء التسلسلي (Backend ثم Frontend) يضيّع أسابيع؛ البديل أن نتفق على الـ Endpoints والأشكال مكتوبةً فيبدأ الطرفان معاً. القاعدة الحاكمة: أي تغيير في العقد يُعلَن ويُوثَّق قبل تنفيذه، ولا يُغيَّر اسم حقل بصمت. كل المسارات تبدأ بـ /api/v1 على http://localhost:8000، وكل الأجسام JSON إلا الرفع.

7.2 جدول الـ Endpoints الكامل

الجدول التالي هو المصدر الوحيد للحقيقة. الرمز yes* يعني أن المصادقة تُفرض فقط عند AUTH_ENABLED=true؛ في وضع العرض (false) يعمل النظام بمستخدم افتراضي دوره safety_officer.

7.5 Pagination و Filtering و Sorting و Date-range

كل مسارات القوائم تعيد غلاف الصفحات نفسه (pagination envelope)؛ الحد الأقصى لـ page_size هو 100.

GET /api/v1/incidents?page=2&page_size=20&incident_type=ppe_violation&sort=-created_at — 200 OKjson
{
  "items": [ { "id": "9d4c1b70-...", "incident_type": "ppe_violation", "severity": "high" } ],
  "total": 24,
  "page": 2,
  "page_size": 20,
  "pages": 2
}
جدول 7-3: معاملات الاستعلام المشتركة لكل مسارات القوائم
المعاملالنوعالمعنى
pageint, ≥1رقم الصفحة، يبدأ من 1
page_sizeint, 1..100عدد العناصر في الصفحة، الافتراضي 20
sortstringحقل الترتيب؛ إشارة - تعني تنازلياً مثل -created_at
date_from / date_toYYYY-MM-DDنطاق زمني مغلق على created_at
incident_typeenumفلترة بنوع الواقعة
severityenumفلترة بدرجة الخطورة
statusenumفلترة بحالة المراجعة
video_idUUIDوقائع فيديو واحد بعينه

نكتب معاملات الترقيم مرة واحدة في مخطط Pydantic قابل لإعادة الاستخدام:

backend/app/schemas/common.pypython
from typing import Generic, TypeVar

from pydantic import BaseModel, Field

T = TypeVar("T")


class PageParams(BaseModel):
    page: int = Field(default=1, ge=1)
    page_size: int = Field(default=20, ge=1, le=100)
    sort: str = "-created_at"


class Paginated(BaseModel, Generic[T]):
    items: list[T]
    total: int = 0
    page: int = 1
    page_size: int = 20
    pages: int = 0

7.6 إبقاء العقد مستقراً أثناء العمل المتوازي

نحمي العقد بخمس أدوات:

  • ملف OpenAPI: يولّده FastAPI تلقائياً على /openapi.json؛ نصدّره إلى docs/openapi.json بعد كل تعديل مقصود.
  • الإصدارات (versioning): أي تغيير كاسر يذهب إلى /api/v2، ولا نحذف حقلاً من v1 إلا بعد إعلان.
  • خادم وهمي (mock server): يبني الـ Frontend على استجابات جاهزة من الـ OpenAPI قبل جهوزية الـ Backend.
  • أنواع مشتركة: ملف frontend/src/types/api.ts (الفصل 14) هو النسخة اليدوية المطابقة للـ VideoOut وغيره.
  • مراجعة العقد: أي PATCH على المسار يمرّ على مسؤول الـ Backend ومسؤول الـ Frontend معاً قبل الدمج.
نصيحة عملية

جرّب الـ Endpoints يدوياً على /docs (Swagger UI) قبل كتابة كود الواجهة.

مثال من الطرفية:

curl — create a processing job and poll itbash
$ curl -X POST http://localhost:8000/api/v1/videos/<video_id>/process
# HTTP/1.1 202 Accepted

$ curl http://localhost:8000/api/v1/jobs/<job_id>
# HTTP/1.1 200 OK  {"status":"running","progress":42.5}

7.7 أخطاء الـ API الموحّدة

شكل خطأ واحد لكل الـ endpoints: رمز آلي ورسالة صديقة، فلا تفحص الواجهة نص الخطأ.

Error response shape — 404 / 409 / 413json
{
  "detail": "Video not found",
  "code": "video_not_found"
}

أخطاء 422 تأتي من Pydantic بـ detail كمصفوفة لكل حقل مرفوض، ونحوّل loc إلى رسالة عربية في الواجهة.

خلاصة الفصل 7

ما تعلّمناه

ثبّتنا جدول الـ Endpoints ورموز الحالة، وأشكال كائنات الرد وغلاف الصفحات، وأدوات إبقاء العقد مستقراً أثناء البناء المتوازي.

ما يجب تنفيذه

  • تثبيت جدول 7-1 في docs/API.md كمرجع ملزم للفريقين.
  • تصدير openapi.json إلى docs/ بعد كل تغيير.
  • كتابة مخطط Paginated[T] في الـ Backend ونظيره في الـ Frontend.
  • توحيد شكل الخطأ عبر exception handler واحد.

المخرجات المتوقعة

  • ملف docs/API.md يطابق SPEC حرفياً.
  • Swagger يعمل على /docs ويغطي كل المسارات.
  • أمثلة JSON قابلة للنسخ في الفصول التالية.

كيف نتحقق من الإنجاز

  • كل مسار في الجدول له رمز نجاح ورموز خطأ محدَّدة.
  • لا يوجد endpoint يعيد 200 عند الفشل.
  • أنواع الـ Frontend تطابق أسماء الحقول دون اختلاف حرف واحد.

أخطاء شائعة

  • تغيير اسم حقل بصمت فيكسر شاشة جاهزة.
  • إعادة أشكال خطأ مختلفة من كل مسار.
  • الخلط بين 202 (قبول غير متزامن) و201 (إنشاء مورد).
  • تجاهل حد page_size الأقصى فيثقل الخادم.

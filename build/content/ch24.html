معالجة الأخطاء والـ Logging والمراقبة

كيف يتصرف النظام عندما تسوء الأمور

النظام الجيد لا يُقاس بعدد المرات التي يعمل فيها، بل بسلوكه عندما يفشل شيء. هذا الفصل يحدّد ماذا يحدث عند تلف فيديو أو نقص checkpoint أو انقطاع قاعدة البيانات، وكيف نجعل السجلات تكفي لتشخيص المشكلة بسرعة دون كشف أي سرّ، وكيف نمنع تكرار الواقعة عند إعادة المحاولة.

24.1 مبدأ عام: الفشل متوقّع وليس استثناءً

معالجة الفيديو عملية طويلة تمرّ عبر ملفات وبطاقة رسوميات وقاعدة بيانات وقرص، وأي واحدة منها قد تفشل. لذلك نتعامل مع الفشل كحالة عادية لها مسار واضح: يُسجَّل الخطأ بسياقه، تُحدَّث حالة الـ job إلى failed، ويُخزَّن error_message، ويستطيع المستخدم رؤية السبب وإعادة المحاولة. الممنوع أن يتوقف النظام بصمت أو أن يترك job عالقاً في running للأبد.

24.3 الـ Logging المنظّم مع سياق

Structured Logging (سجلات منظّمة): كتابة السجلات بصيغة حقول ثابتة (وقت، مستوى، رسالة، job_id، video_id) بدل نصوص حرّة. الفائدة أن البحث عن كل سطور job واحد يصبح استعلاماً بسيطاً على job_id. نمنع تماماً تسجيل كلمات المرور أو التوكنات أو مفاتيح S3_SECRET_ACCESS_KEY، ونكتفي بذكر المعرّفات.

24.4 الأخطاء القابلة للاسترجاع وغير القابلة

Recoverable error (خطأ قابل للاسترجاع): خطأ مؤقّت يمكن أن ينجح لو أُعيد المحاولة بعد فترة، مثل انقطاع اتصال قصير بقاعدة البيانات أو مشكلة شبكة. وNon-recoverable error (غير قابل للاسترجاع): خطأ ثابت لا يتغيّر بإعادة المحاولة، مثل فيديو تالف أو مسار checkpoint خاطئ. القاعدة: نعيد المحاولة على الأول فقط، وحدّه الأعلى JOB_MAX_RETRIES، مع تأخير متزايد بين المحاولات، وبعد استنفاد المحاولات تُثبَّت الحالة failed.

24.5 منع تكرار الوقائع بعد إعادة المحاولة

هذا أخطر تفصيل. لو أُعيد تشغيل job بعد فشله في منتصف الفيديو، فقد يُنشئ وقائع جديدة لنفس الحدث الذي أُنشئت له وقائع في المحاولة الأولى، فيتضاعف السجل ويصبح غير موثوق. لذلك نتبع قاعدتين معاً: الأولى نحذف أو نتجاهل وقائع المحاولة الفاشلة لنفس الـ job قبل إعادة التشغيل، والثانية نحترم INCIDENT_COOLDOWN_SECONDS داخل نفس الفيديو بحيث لا تُنشأ واقعتان لنفس النوع داخل فترة التهدئة. بهذا تكون إعادة المحاولة آمنة (idempotent بالنسبة للوقائع).

24.6 مراقبة صحة الخدمة

نراقب ثلاث نقاط: GET /api/v1/health للتأكد من حياة الـ API واتصاله بقاعدة البيانات، وحالة الـ jobs لرصد أي job عالق في running، ونسبة فشل الـ Jobs كمؤشر عام على صحة خط المعالجة.

24.7 ملف الـ Logging

هذا الملف يضبط سجلاً موحّداً لكل التطبيق، ويضيف job_id و video_id تلقائياً عند توفّرهما، ويحجب أي حقل حسّاس من الظهور.

backend/app/core/logging.pypython
import logging
import sys

# Never let these values reach the log stream.
SENSITIVE_KEYS = {"password", "token", "authorization", "secret_key", "s3_secret_access_key"}


def configure_logging(level: str = "INFO") -> None:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(
        logging.Formatter(
            "%(asctime)s %(levelname)s %(name)s "
            "job_id=%(job_id)s video_id=%(video_id)s %(message)s"
        )
    )
    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(level.upper())


def scrub(extra: dict) -> dict:
    """Drop sensitive fields before they are written to the log."""
    return {
        key: value
        for key, value in extra.items()
        if key.lower() not in SENSITIVE_KEYS
    }


def job_logger(name: str, job_id: str | None = None, video_id: str | None = None):
    """Return a logger that always carries the job context."""
    logger = logging.getLogger(name)
    return logging.LoggerAdapter(
        logger, {"job_id": job_id or "-", "video_id": video_id or "-"}
    )

24.8 ملف الأخطاء المخصّصة

نعرّف أنواع الأخطاء بأنفسنا حتى نفرّق بين ما يُعاد تشغيله وما لا يُعاد، ولنعطي المستخدم رسالة واضحة بدل تفاصيل داخلية.

backend/app/core/errors.pypython
class SafeVisionError(Exception):
    """Base class for all application errors."""

    code = "safevision_error"
    recoverable = False

    def __init__(self, message: str, detail: str | None = None):
        super().__init__(message)
        self.message = message
        self.detail = detail


class InvalidVideoError(SafeVisionError):
    code = "invalid_video"
    recoverable = False  # a corrupt file will never succeed on retry


class ModelCheckpointMissing(SafeVisionError):
    code = "checkpoint_missing"
    recoverable = False  # fix the path, then retry manually


class InsufficientGpuMemory(SafeVisionError):
    code = "gpu_oom"
    recoverable = True  # retry on CPU or after freeing memory


class TransientDatabaseError(SafeVisionError):
    code = "db_unavailable"
    recoverable = True  # connection blips succeed on retry


class EvidenceStorageError(SafeVisionError):
    code = "evidence_storage_failed"
    recoverable = True  # the incident is kept and evidence is retried


def should_retry(error: Exception, attempt: int, max_retries: int) -> bool:
    if not isinstance(error, SafeVisionError):
        return attempt < max_retries
    return error.recoverable and attempt < max_retries

خلاصة الفصل 24

ما تعلّمناه

غطّينا تسعة سيناريوهات فشل بسلوك واضح، وفرّقنا بين الأخطاء القابلة للاسترجاع وغير القابلة، وربطنا السجلات بـ job_id، ومنعنا كشف الأسرار، وضبطنا إعادة محاولة آمنة لا تكرّر الوقائع.

ما يجب تنفيذه

  • كتابة backend/app/core/logging.py وerrors.py.
  • ربط كل خطأ في الـ worker بـ error_message وحالة failed.
  • تطبيق حذف وقائع المحاولة الفاشلة قبل إعادة التشغيل.
  • التحقق من عدم تسجيل أي حقل حسّاس.

المخرجات المتوقعة

  • سجلات منظّمة قابلة للبحث بـ job_id.
  • رسائل خطأ واضحة تظهر للمستخدم بدل تفاصيل داخلية.
  • جدول استكشاف أخطاء معتمد من الفريق.

كيف نتحقق من الإنجاز

  • تشغيل job بمسار model خاطئ ومشاهدة الفشل الواضح.
  • إعادة تشغيل job فاشل والتأكد من عدم تكرار الوقائع.
  • البحث عن أي كلمة مرور في السجلات وعدم العثور عليها.

أخطاء شائعة

  • تسجيل كائن الطلب كاملاً بما فيه التوكن.
  • إعادة المحاولة على خطأ ثابت بلا فائدة.
  • إعادة المحاولة دون حذف وقائع المحاولة السابقة.
  • ترك job عالقاً في running دون مهلة زمنية.

تقييم الـ AI وأداء النظام

تقييم الـ Models منفصلة عن تقييم التطبيق، وبأرقام حقيقية فقط

هذا الفصل يحدّد كيف نقيس الجودة، وما هي المقاييس التي تُقنع لجنة المناقشة. القاعدة الأولى: نفصل تقييم الـ Model (هل الكشف نفسه دقيق؟) عن تقييم التطبيق (هل النظام يُنتج وقائع مفيدة؟). القاعدة الثانية والأهم: لا نكتب أي رقم لم نقِسه فعلاً؛ كل الجداول هنا فارغة وموسومة (يُملأ بعد التجربة).

23.1 لماذا نفصل تقييم الـ Model عن تقييم النظام

الـ Model يرى إطارات ويعيد صناديق وفئات. لكن المستخدم لا يرى الصناديق، بل يرى واقعة لها وقت ودرجة خطورة وحالة مراجعة. بينهما قواعد السلامة (عدد الإطارات المتتالية، فترة التهدئة، منطقة الخطر) والتتبّع واقتطاع الدليل. لذلك قد يكون الـ Model ممتازاً على مستوى الكشف، ومع ذلك ينتج نظاماً مزعجاً لكثرة الوقائع المكرّرة أو المفقودة.

23.2 مقاييس الكشف: Precision و Recall و F1

Precision (الدقة): من بين كل ما كشفه الـ Model، ما نسبة ما كان صحيحاً فعلاً؟ Recall (الاستدعاء): من بين كل الأهداف الحقيقية، ما نسبة ما نجح في كشفها؟ و F1 هو المتوسط التوافقي بينهما ويعطي رقماً واحداً متوازناً. وفي سياق السلامة، الـ Recall غالباً أهم، لأن تفويت حادث أخطر من إنذار زائد.

23.3 Confusion Matrix و mAP

Confusion Matrix (مصفوفة الالتباس): جدول يقارن التنبؤ بالحقيقة، ويُظهر أين يخطئ الـ Model: هل يخلط بين "خوذة" و"بدون خوذة"؟ أم يفشل في كشف الدخان؟ هذا الجدول أنفع من رقم واحد لأن كل خطأ له وزن مختلف في السلامة. أمّا mAP فهو مقياس قياسي للكشف يجمع الدقة عبر عتبات الثقة، ويُستخدم لمقارنة نسختين من الـ Model على نفس مجموعة الاختبار.

23.4 مقاييس التتبّع (Tracking)

  • ID switches: عدد المرات التي "قفز" فيها معرّف التتبّع من شخص إلى آخر.
  • Track fragmentation: انقطاع مسار شخص ثم بدؤه من جديد بنفس المعرّف أو بمعرّف آخر.
  • Track continuity: نسبة الإطارات التي بقي فيها المسار متصلاً.

هذه المقاييس مهمة لأن خطأ التتبّع يفسد قواعد "عدد الإطارات المتتالية"، فقد تُدمج واقعتان أو تتكرّر واقعة واحدة عدة مرات بسبب انقطاع المسار.

23.5 التقييم على مستوى الواقعة

هنا نقيس ما يراه المستخدم فعلاً: هل أنشأ النظام واقعة عند حدوث المخالفة؟ هل فقد واقعة؟ هل كرّرها؟ نُعطي كل واقعة حقيقية في الفيديو صفة مرجعية يدوياً، ثم نقارنها بمخرجات النظام بعد قواعد السلامة. النتيجة ثلاث فئات: واقعة صحيحة (true incident)، واقعة زائفة (false incident)، وواقعة مفقودة (missed incident). هذا هو المقياس الذي يهم مسؤول السلامة، وليس mAP.

23.7 لماذا لا تضمن mAP العالية نظام إدارة وقائع مفيداً

هذا سؤال تتوقّعه اللجنة، والإجابة يجب أن تكون واضحة. الـ mAP يقيس الكشف على مجموعة اختبار ثابتة بإعدادات مثالية، لكن النظام الحقيقي يختلف في عدة أمور:

  • العتبات: عتبة ثقة منخفضة ترفع الـ Recall وتغرق المراجع في إنذارات كاذبة، والعكس صحيح.
  • القواعد الزمنية: عدد الإطارات المتتالية وفترة التهدئة يحدّدان إن كانت الواقعة تُنشأ أم تُدمج أو تُكرّر.
  • التتبّع: انقطاع المسار أو قفز المعرّف يفسد ربط الإطارات في واقعة واحدة.
  • التوزيع الحقيقي: بيانات المصنع الحقيقية قد تختلف كثيراً عن بيانات الاختبار (إضاءة، زوايا، ازدحام).
  • جودة الدليل: واقعة صحيحة بلا صورة دليل واضحة أقل فائدة للمراجع من واقعة مع دليل واضح.

لذلك نعرض دائماً مقياسين معاً: mAP للـ Model، وتقييم على مستوى الواقعة للنظام ككل.

23.8 خطة تقييم خط الأنابيب الكامل

نقيّم النظام على مقاطع مصنّفة حسب الظرف: إضاءة عادية وضعيفة، حجب جزئي (occlusion)، زوايا كاميرا مختلفة، مشاهد مزدحمة بعدة عمال، وحالات صعبة (خوذة قريبة من نفس لون الخلفية). لكل ظرف نُسجّل نفس المقاييس، لأن ضعف الأداء غالباً يظهر في ظرف واحد فقط.

23.9 سكربت التقييم

هذا السكربت يقرأ ملف الحقيقة المرجعية (ground_truth.json) وملف تنبؤات النظام، ثم يحسب المقاييس ويطبعها. مخرجاته شكلية فقط كما يظهر في التعليقات: لا يحتوي على أي رقم حقيقي لأن الأرقام تأتي من التشغيل الفعلي.

scripts/evaluate_model.pypython
"""Compute detection metrics from ground truth and system predictions.

Usage:
    python scripts/evaluate_model.py --truth data/gt.json --pred data/pred.json

Expected output shape (numbers are produced only by a real run):
    class: ppe_violation
      precision: 0.0000
      recall:    0.0000
      f1:        0.0000
      tp: 0  fp: 0  fn: 0
"""
import argparse
import json


def load_pairs(path):
    with open(path, encoding="utf-8") as handle:
        return json.load(handle)["items"]


def iou(box_a, box_b):
    ax1, ay1, ax2, ay2 = box_a
    bx1, by1, bx2, by2 = box_b
    ix1, iy1 = max(ax1, bx1), max(ay1, by1)
    ix2, iy2 = min(ax2, bx2), min(ay2, by2)
    inter = max(0, ix2 - ix1) * max(0, iy2 - iy1)
    area_a = (ax2 - ax1) * (ay2 - ay1)
    area_b = (bx2 - bx1) * (by2 - by1)
    union = area_a + area_b - inter
    return inter / union if union else 0.0


def match_frame(truth_items, pred_items, iou_threshold=0.5):
    """Greedy one-to-one matching per frame; returns tp, fp, fn counts."""
    used = set()
    tp = 0
    for t in truth_items:
        best_idx, best_iou = -1, iou_threshold
        for idx, p in enumerate(pred_items):
            if idx in used or p["class_name"] != t["class_name"]:
                continue
            score = iou(t["bbox"], p["bbox"])
            if score >= best_iou:
                best_idx, best_iou = idx, score
        if best_idx >= 0:
            used.add(best_idx)
            tp += 1
    return tp, len(pred_items) - len(used), len(truth_items) - tp


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--truth", required=True)
    parser.add_argument("--pred", required=True)
    parser.add_argument("--iou", type=float, default=0.5)
    args = parser.parse_args()

    truth = load_pairs(args.truth)
    pred = load_pairs(args.pred)

    tp = fp = fn = 0
    for frame_number in {t["frame_number"] for t in truth}:
        t_items = [t for t in truth if t["frame_number"] == frame_number]
        p_items = [p for p in pred if p["frame_number"] == frame_number]
        a, b, c = match_frame(t_items, p_items, args.iou)
        tp, fp, fn = tp + a, fp + b, fn + c

    precision = tp / (tp + fp) if (tp + fp) else 0.0
    recall = tp / (tp + fn) if (tp + fn) else 0.0
    f1 = 2 * precision * recall / (precision + recall) if (precision + recall) else 0.0

    # These are format examples; real values appear only after a real run.
    print(f"precision: {precision:.4f}")
    print(f"recall:    {recall:.4f}")
    print(f"f1:        {f1:.4f}")
    print(f"tp: {tp}  fp: {fp}  fn: {fn}")


if __name__ == "__main__":
    main()

خلاصة الفصل 23

ما تعلّمناه

فرّقنا بين مقاييس الـ Model (Precision, Recall, F1, mAP, Confusion Matrix) ومقاييس التتبّع ومقاييس النظام، وثبّتنا أن التقييم الحقيقي يحدث على مستوى الواقعة. وشرحنا لماذا لا تضمن mAP عالية نظام إدارة وقائع مفيداً.

ما يجب تنفيذه

  • تجهيز ملف الحقيقة المرجعية لفيديو التقييم.
  • تشغيل scripts/evaluate_model.py وتسجيل مخرجاته.
  • تعبئة جداول 23-3 و23-4 و23-5 بعد التشغيل الفعلي فقط.
  • قياس زمن المعالجة وFPS على الجهاز المستخدم فعلاً.

المخرجات المتوقعة

  • تقرير تقييم يحتوي مقاييس الـ Model ومقاييس الواقعة معاً.
  • جدول أداء تشغيلي يوضّح زمن المعالجة ونسبة فشل الـ Jobs.
  • ملاحظات صريحة عن الظروف التي ضعف فيها الأداء.

كيف نتحقق من الإنجاز

  • كل رقم في التقرير له مصدر قياس مكتوب.
  • لا يوجد جدول نتيجة ممتلئ قبل تنفيذ التجربة.
  • التمييز واضح بين mAP وبين مقياس الواقعة.

أخطاء شائعة

  • عرض mAP فقط وإغفال تقييم الواقعة.
  • قياس الأداء على جهاز GPU وإعلانه كنتيجة عامة.
  • مقارنة نتائج من مجموعات اختبار مختلفة.
  • كتابة أرقام متوقّعة قبل التشغيل.

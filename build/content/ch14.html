CH14 · FRONTEND ARCHITECTURE

معمارية الـ Frontend بـ React و TypeScript

بنية قابلة للصيانة، هوية بصرية صناعية، وتجربة استخدام واضحة

هذا الفصل يضع هيكل الواجهة قبل كتابة مكوّناتها: تقسيم الكود، وتنظيم المسارات، ومطابقة أنواع TypeScript مع عقد الـ API حرفياً، وتوضيح الشاشات العشر قبل تنفيذها.

14.1 بنية تطبيق React

نقسّم src حسب الميزة (feature) لا حسب نوع الملف فقط، فيصبح كل جزء مسؤولاً عن نفسه:

جدول 14-1: طبقات الـ Frontend ومسؤولية كل طبقة
المجلّدالمسؤولية

hooks/منطق مشترك: الترقيم، الاستطلاع، الجلب، التنبيهات
types/أنواع مطابقة لعقد الـ API، تُستورد في كل مكان

14.5 أنواع TypeScript المشتركة

هذا الملف هو الجسر بين عقد الـ API والواجهة. كل واجهة هنا تطابق كائن رد في SPEC.md بنفس أسماء الحقول؛ أي اختلاف حرف واحد خطأ يجب إصلاحه.

frontend/src/types/api.tstypescript
// Mirrors SPEC.md response shapes exactly. Do not rename fields.

export type VideoStatus = "uploaded" | "processing" | "processed" | "failed";
export type JobStatus = "queued" | "running" | "completed" | "failed" | "cancelled";
export type IncidentType = "ppe_violation" | "fire_smoke" | "machine_proximity";

}

14.7 الحالات والتجربة والهوية البصرية

لكل قائمة أو بطاقة ثلاث حالات صريحة بمكوّنات موحّدة:

جدول 14-3: الحالات الثلاث ومكوّناتها
الحالةالمكوّنالقاعدة
LoadingSpinnerهيكل ثابت يمنع اهتزاز الصفحة أثناء الجلب
ErrorErrorStateرسالة عربية + زر إعادة المحاولة، دون كشف تفاصيل تقنية
EmptyEmptyStateنص يشرح الخطوة التالية ("ارفع فيديو للبدء") بدل جدول فارغ
  • النماذج (forms): تحقق قبل الإرسال وزر معطّل أثناءه لمنع الطلب المزدوج.
  • الإشعارات (Toast): تأكيد نجاح/فشل الإجراء من سياق واحد أعلى الشجرة.
  • حالة المصادقة: تتبع VITE_ENABLE_AUTH؛ عند false نتجاوز الدخول، وعند true نحمي المسارات ونرسل التوكن.
  • التجاوب وإمكانية الوصول: تخطيط شبكي، تباين كافٍ، نصوص بديلة، وتنقّل بلوحة المفاتيح.

الهوية البصرية: Dark Navy للبنية، Teal للمعلومات، Orange للتحذير، Red للخطر، وخلفيات محايدة؛ بلا تدرجات أو حركات زائدة. ألوان الخطورة تتبع الـ enum: low, medium, high, critical.

لا روابط إنتاج داخل المكوّنات

العنوان يأتي دائماً من import.meta.env.VITE_API_BASE_URL عبر عميل واحد في api/client.ts، ولا يُكتب أي عنوان داخل مكوّن.

خلاصة الفصل 14

ما تعلّمناه

قسّمنا الـ Frontend حسب الميزة، ورسمنا خريطة الصفحات، ووصفنا الشاشات العشر، وأثبتنا أنواع TypeScript المطابقة للـ API، وثبّتنا حالات التحميل/الخطأ/الفراغ والهوية البصرية.

ما يجب تنفيذه

  • إنشاء مجلّدات features/hooks/api/types كما في الشجرة.
  • نسخ types/api.ts حرفياً وربطه بعميل الـ API.
  • بناء المكوّنات العامة (Button, Table, EmptyState, ErrorState, Spinner).
  • تعريف المسارات مع حارس مصادقة يقرأ VITE_ENABLE_AUTH.

المخرجات المتوقعة

  • هيكل frontend/src كامل وفارغ من الأخطاء النوعية.
  • ملف أنواع واحد يطابق SPEC دون اختلاف.
  • تخطيط عام (Layout) يعمل على الشاشات المختلفة.

كيف نتحقق من الإنجاز

  • npm run build ينجح دون أخطاء TypeScript.
  • كل صفحة من العشر لها مسار ومكوّن محدَّد.
  • لا يوجد عنوان API مكتوب داخل أي مكوّن.

أخطاء شائعة

  • خلط أنواع الواجهة بأسماء حقول مختلفة عن الـ API.
  • كتابة عناوين الـ Backend داخل المكوّنات.
  • إهمال حالة الفراغ فيظهر جدول فارغ بلا شرح.
  • مبالغة في الحركات والتدرجات فتشتّت المستخدم.

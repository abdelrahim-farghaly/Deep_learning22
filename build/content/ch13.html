CH13 · INCIDENT LIFECYCLE

دورة حياة الواقعة والمراجعة البشرية

detected ثم pending_review ثم confirmed أو rejected ثم closed

الواقعة لا تنتهي عند كشفها. لها دورة حياة واضحة تنقلها من حالة تلقائية إلى قرار بشري موثّق. هذا الفصل يوضّح هذه الدورة، وما يفعله مسؤول السلامة، ولماذا نسجّل كل إجراء.

13.1 دورة حياة الواقعة

خمس حالات فقط، وكل انتقال مسموح مذكور صراحةً. الـ pipeline ينشئ الواقعة بحالة detected، ثم تُصبح pending_review في طابور المراجعة، ثم يقرّر المسؤول فتنتقل إلى confirmed أو rejected، وأخيراً إلى closed.

detectedتلقائي من الـ pipeline
pending_reviewبانتظار مسؤول السلامة
confirmedتأكيد بشري
rejectedرفض بشري
closedإغلاق نهائي

جدول 13-1: الانتقالات المسموحة وسبب رفض غيرها
الانتقالالإجراء المُسجَّلالقاعدة
detected → pending_review—تلقائي عند دخول الواقعة طابور المراجعة
pending_review → confirmedconfirmمراجعة بشرية بعد فحص الدليل
pending_review → rejectedrejectمراجعة بشرية: إنذار كاذب

rejected → closedcloseإغلاق بعد الرفض
انتقال غير مسموح

لا يمكن الانتقال من detected مباشرةً إلى confirmed، ولا إعادة فتح واقعة closed. أي محاولة كذلك تُرفض بحالة 409.

13.2 ماذا يفعل مسؤول السلامة

  • يفتح قائمة الوقائع GET /api/v1/incidents ويفلترها بالنوع والخطورة والحالة والتاريخ.
  • يفتح الواقعة GET /api/v1/incidents/{incident_id} فيرى الدليل والزمن (started_at_seconds) والفيديو المصدر.
  • يشاهد صورة الدليل GET /api/v1/evidence/{evidence_id}/file.
  • يؤكّد أو يرفض أو يضيف ملاحظة عبر PATCH /api/v1/incidents/{incident_id}.
  • يبحث تاريخياً عن المخالفات المتكرّرة لنفس الموقع أو المسار.

في وضع العرض التوضيحي (AUTH_ENABLED=false) يتصرّف النظام كأن مستخدم safety_officer افتراضي هو المراجع، ويكون reviewer_id قابلاً لأن يكون NULL. عند تفعيل المصادقة يُسجَّل معرّف المستخدم الفعلي.

13.3 لماذا نسجّل كل إجراء (Auditability)

كل تغيير حالة يُلحق صفاً جديداً في incident_reviews يحمل الفاعل والحالة السابقة والجديدة والملاحظة. هذا يعطي: تتبّعاً كاملاً (من فعل ماذا ومتى)، ومسؤولية واضحة، وإمكانية إعادة بناء تاريخ الواقعة. لا نعدّل الصفوف القديمة ولا نحذفها أبداً.

وبالاستعلام عن incident_reviews نعرف من أكّد كل واقعة ومتى، وهو ما تحتاجه أي لجنة تدقيق لاحقاً. أما البحث التاريخي في جدول incidents (بالنوع والخطورة والحالة ونطاق التاريخ) فيعتمد على الفهارس المذكورة في الفصل 8.

على الـ Frontend: بعد الردّ الناجح تُحدَّث حالة الواقعة في الجدول إلى confirmed، ويظهر صف المراجعة الجديد في سجلّها، ويُزاح العنصر من قائمة pending_review.

backend/app/api/v1/endpoints/incidents.pypython
# backend/app/api/v1/endpoints/incidents.py (PATCH excerpt)
import uuid
from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy.orm import Session
from app.db.session import get_db
from app.models.enums import IncidentStatus, ReviewAction
from app.models.incident import Incident
from app.models.incident_review import IncidentReview
from app.schemas.incident import IncidentOut, IncidentPatch

router = APIRouter(prefix="/incidents", tags=["incidents"])

# target status -> (required current status, audit action)
TRANSITIONS = {
    IncidentStatus.confirmed: (IncidentStatus.pending_review, ReviewAction.confirm),
    IncidentStatus.rejected: (IncidentStatus.pending_review, ReviewAction.reject),
    IncidentStatus.closed: (IncidentStatus.confirmed, ReviewAction.close),
}


@router.patch("/{incident_id}", response_model=IncidentOut)
def patch_incident(incident_id: uuid.UUID, payload: IncidentPatch,
                   db: Session = Depends(get_db)) -> IncidentOut:
    incident = db.get(Incident, incident_id)
    if incident is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "incident not found")

    new_status = IncidentStatus(payload.status) if payload.status else incident.status
    if new_status != incident.status and new_status not in TRANSITIONS:
        raise HTTPException(status.HTTP_409_CONFLICT, "status cannot be set directly")
    if new_status != incident.status:
        required, action = TRANSITIONS[new_status]
        if incident.status != required:
            raise HTTPException(status.HTTP_409_CONFLICT, "invalid status transition")
        db.add(IncidentReview(
            incident_id=incident.id, reviewer_id=payload.reviewer_id, action=action,
            previous_status=incident.status, new_status=new_status, note=payload.note))
        incident.status = new_status
    elif payload.note:
        db.add(IncidentReview(
            incident_id=incident.id, reviewer_id=payload.reviewer_id,
            action=ReviewAction.comment, previous_status=incident.status,
            new_status=incident.status, note=payload.note))

    db.commit()
    db.refresh(incident)
    return IncidentOut.model_validate(incident)

# backend/app/models/incident_review.py
import uuid
from datetime import datetime
from sqlalchemy import DateTime, Enum, ForeignKey, Text, func
from sqlalchemy.dialects.postgresql import UUID
from sqlalchemy.orm import Mapped, mapped_column, relationship
from app.db.base import Base
from app.models.enums import IncidentStatus, ReviewAction


class IncidentReview(Base):
    __tablename__ = "incident_reviews"

    id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    incident_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("incidents.id", ondelete="CASCADE"), nullable=False)
    reviewer_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("users.id"))
    action: Mapped[ReviewAction] = mapped_column(
        Enum(ReviewAction, name="review_action"), nullable=False)
    previous_status: Mapped[IncidentStatus | None] = mapped_column(
        Enum(IncidentStatus, name="incident_status"))
    new_status: Mapped[IncidentStatus | None] = mapped_column(
        Enum(IncidentStatus, name="incident_status"))
    note: Mapped[str | None] = mapped_column(Text)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())

    incident = relationship("Incident", back_populates="reviews")

13.5 الكشف الآلي يساعد المراجعة ولا يحلّ محل الحكم المهني

حدّ أساسي في النظام

النظام أداة فرز ومساعدة، وليس بديلاً عن مسؤول السلامة. الكشف الآلي قد يُخطئ (إنذار كاذب) وقد يُفوّت (حدث مفقود)، والقرار النهائي دائماً بشري. لذلك لا تنتقل أي واقعة إلى confirmed تلقائياً، ولا يُبنى أي إجراء تأديبي على مخرجات الـ Model وحدها. الواجهة تعرض دائماً عبارة واضحة بأن النتيجة كشف آلي يحتاج مراجعة.

عملياً، تعرض الواجهة شارة "كشف آلي" بجانب كل واقعة، وتطلب من المراجع فحص الدليل قبل أي قرار. هذا التصميم يحمي الفريق من الادّعاء بأن النظام يحكم على العاملين بدل أن يساعدهم.

خلاصة الفصل 13

ما تعلّمناه

دورة حياة الواقعة بانتقالاتها الخمس، وما يفعله مسؤول السلامة، ولماذا نسجّل كل إجراء في incident_reviews، وأن الكشف الآلي يدعم المراجعة ولا يستبدلها.

ما يجب تنفيذه

  • كتابة incident_review.py وجدول incident_reviews.
  • تنفيذ PATCH /api/v1/incidents/{incident_id} مع التحقق من الانتقالات.
  • إظهار الدليل والزمن والفيديو المصدر في صفحة الواقعة.

المخرجات المتوقعة

  • واقعة قابلة للتأكيد أو الرفض مع صف مراجعة لكل إجراء.
  • سجل تدقيق كامل قابل للعرض.

كيف نتحقق من الإنجاز

  • تأكيد واقعة يُلحق صفاً بالإجراء confirm والحالة الجديدة confirmed.
  • محاولة انتقال غير مسموح تُرجع 409.
  • لا توجد واقعة تُصبح confirmed بدون صف مراجعة.

أخطاء شائعة

  • تأكيد الوقائع آلياً من الـ pipeline.
  • تعديل أو حذف صفوف المراجعة القديمة.
  • السماح بانتقالات حالة غير معرّفة.
  • تقديم الكشف الآلي كحكم نهائي بدل دعم القرار البشري.

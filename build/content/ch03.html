حزمة التقنيات واختيار الأدوات

لماذا اخترنا كل أداة، وما البدائل، وما هو مطلوب في الـ MVP

اختيار التقنية ليس "أيّ شيء يعمل"، بل قرار يجب أن نستطيع تبريره. في هذا الفصل نعرض كل أداة استخدمناها، وما وظيفتها، ولماذا اخترناها بدلاً من بديل آخر، وهل هي مطلوبة في الـ MVP أم اختيارية. الهدف أن يكون كل عضو قادراً على الدفاع عن كل اختيار أمام لجنة المناقشة.

3.3 لماذا Python للـ Backend وللذكاء الاصطناعي معاً

Python: لغة برمجة عالية المستوى تُقرأ مثل الإنجليزية تقريباً. اخترناها لأن عالم الذكاء الاصطناعي كله مبني حولها: PyTorch وUltralytics وOpenCV كلها مكتبات Python في المقام الأول. لو اخترنا لغة أخرى للـ Backend لكنا مضطرين لتشغيل عمليتين بلغتين مختلفتين والتنسيق بينهما، وهذا تعقيد لا حاجة له.

النسخة المستهدفة Python 3.11 لأنها توازن بين حداثة الميزات واستقرار المكتبات. نستخدم venv (بيئة افتراضية) لعزل مكتبات المشروع عن مكتبات النظام، وهذا موضوع الفصل الخامس بالتفصيل.

3.4 حزمة الذكاء الاصطناعي والرؤية الحاسوبية

  • PyTorch: المحرّك الذي يشغّل أوزان الشبكات العصبية. اخترناه لأنه الأكثر استخداماً في الأبحاث والمراجع، ولأن Ultralytics مبنية عليه.
  • Ultralytics YOLO: مكتبة جاهزة للكشف عن الأجسام. توفّر لنا دالة واحدة للتشغيل ودالة تتبّع model.track، فلا نكتب منطق الشبكة بأنفسنا.
  • ByteTrack: خوارزمية تتبّع تُعطي كل شخص معرّفاً ثابتاً عبر الإطارات. مهمّة لأن "شخص بدون خوذة" يجب أن يبقى نفس الشخص عبر الإطارات لنحسب مدة المخالفة.
  • OpenCV: قراءة الفيديو، استخراج الإطارات، تغيير الحجم، وكتابة الإطارات كصور دليل.
  • NumPy: العمليات العددية على المصفوفات، وتُستخدم داخلياً في حساب التداخل والمسافات.
  • Pandas: تجميع الوقائع في جداول للتقارير اليومية والتصدير بصيغة CSV.
أين تُشغَّل هذه المكتبات؟

داخل عملية الـ worker لا داخل عملية الـ API. تشغيل PyTorch في عملية الـ API يستهلك الذاكرة ويجمّد الطلبات، لذلك الفصل إلزامي.

3.5 حزمة الـ Backend وقاعدة البيانات

  • FastAPI: إطار ويب حديث يبني الـ API بسرعة، ويولّد توثيق Swagger تلقائياً من أنواع البيانات. يوفّر تحققاً تلقائياً من المدخلات وأداءً عالياً.
  • Uvicorn: الخادم الذي يشغّل تطبيق FastAPI فعلاً. الأمر المعتاد uvicorn app.main:app --reload.
  • Pydantic v2: يتحقق من شكل البيانات الداخلة والخارجة عبر نماذج مكتوبة بأنواع صريحة، ويُعيد رسائل خطأ دقيقة. وpydantic-settings يقرأ متغيّرات البيئة ويحوّلها إلى كائن إعدادات واحد.
  • SQLAlchemy 2.0: يربط كود Python بجداول PostgreSQL دون كتابة SQL يدوي لكل استعلام، ويسمح بتعريف الجداول كأصناف (classes).
  • Alembic: يتتبّع كل تغيير في مخطط قاعدة البيانات كملف migration يمكن تطبيقه أو التراجع عنه، فيتزامن الفريق دون حذف البيانات.
  • PostgreSQL 16: قاعدة بيانات علائقية قوية تدعم UUID والأنواع والعناصر الجزئية الفريدة (partial unique index) التي نحتاجها لمنع تشغيل مهمّتين على نفس الفيديو. اخترناها على SQLite لأن SQLite لا تكفي لبيئة متعددة العمليات، وعلى MySQL لتقاربها مع متطلبات المشروع.
  • psycopg (v3): المشغّل الذي يربط SQLAlchemy بـ PostgreSQL. نسخة v3 هي الحديثة والمستقرة.
  • JWT + bcrypt: للمصادقة. الـ JWT رمز دخول موقَّع، وbcrypt تجزئة كلمات المرور بحيث لا تُخزَّن أبداً كنص صريح. هذه الحزمة اختيارية خلف علم AUTH_ENABLED.

3.6 حزمة الـ Frontend

  • React 18: مكتبة بناء واجهات تعتمد على المكوّنات، فنبني كل صفحة من قطع صغيرة قابلة لإعادة الاستخدام.
  • TypeScript 5: نسخة من JavaScript بأنواع صريحة، تكتشف أخطاء الوصول لحقول غير موجودة قبل التشغيل. مهمّة جداً لأن عقد الـ API كبير.
  • Vite 5: أداة تشغيل وبناء سريعة تُحدّث الصفحة فوراً عند تعديل الكود.
  • Tailwind CSS 3: تنسيق الواجهة بفئات جاهزة مكتوبة داخل الـ HTML مباشرة، بلا ملفات CSS ضخمة.
  • Recharts: رسم المخططات البيانية لمؤشرات الـ Analytics بأسلوب مكوّنات React.
  • Axios: إرسال طلبات HTTP إلى الـ Backend مع تعامل مريح مع الأخطاء والرؤوس.
  • react-router-dom v6: التنقل بين صفحات التطبيق دون إعادة تحميل الصفحة.

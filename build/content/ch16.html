التحديثات الفورية وحالة المعالجة

Polling الآن، WebSocket لاحقاً

بعد بدء معالجة فيديو، يريد المستخدم أن يرى نسبة التقدّم تتحرّك دون إعادة تحميل الصفحة. هذا الفصل يقارن الطرق الثلاثة لتحديث الحالة، ويوضّح لماذا نختار Polling في الـ MVP، وكيف نكتبه دون تسريب مؤقتات، وكيف نترك الباب مفتوحاً لـ WebSocket لاحقاً.

16.2 لماذا نختار Polling للـ MVP

معدّل تحديث حالة الـ job ليس مرتفعاً، وعدد المستخدمين في العرض التوضيحي صغير، والفائدة من WebSocket لا تبرّر تعقيده الآن. الـ Polling يُبنى في دقائق، ويعمل مع نفس الـ endpoints الموجودة (GET /api/v1/jobs/{job_id}) دون أي تغيير في الـ Backend. نستخدم فترة قصيرة نسبياً (٣ ثوانٍ) أثناء المعالجة، ونتوقف تماماً عند وصول الـ job إلى حالة نهائية.

16.3 خطّاف متابعة حالة الـ Job

نبني الخطّاف على usePolling من الفصل السابق، ونمرّر له دالة shouldStop تُرجِع true عند الحالات النهائية (completed, failed, cancelled). هذا يمنع استمرار الطلبات بلا داعٍ بعد انتهاء العمل.

frontend/src/hooks/useJobStatus.tstypescript
import { useCallback } from "react";
import { api } from "../api/client";
import type { JobOut } from "../types/api";
import { usePolling } from "./usePolling";

const TERMINAL: string[] = ["completed", "failed", "cancelled"];

export function useJobStatus(jobId: string | null, intervalMs = 3000) {
  const fetcher = useCallback(async () => {
    const { data } = await api.get<JobOut>(`/api/v1/jobs/${jobId}`);
    return data;
  }, [jobId]);

  const shouldStop = useCallback((job: JobOut) => TERMINAL.includes(job.status), []);

  return usePolling<JobOut>(fetcher, {
    enabled: Boolean(jobId),
    intervalMs,
    shouldStop,
  });
}

16.4 تجنّب تسريب المؤقتات والـ Backoff

الخطأ الأشهر هو ترك setInterval يعمل بعد مغادرة الصفحة، فيستمر الطلب إلى خادم أُغلق أو مستخدم سجّل خروجه. لذلك نستخدم setTimeout متسلسلاً لا setInterval، ونُنظّف المؤقت في دالة الإرجاع الخاصة بـ useEffect. عند فشل الطلب نطبّق تراجعاً بسيطاً بمضاعفة الفترة قبل المحاولة التالية بدل إغراق الخادم بطلبات فاشلة.

  • خطّاف واحد مسؤول عن المؤقت، ولا يُنشئ المؤقت إلا عند تفعيل enabled.
  • إلغاء الطلب الجاري عبر علم cancelled حتى لا نُحدّث مكوّناً أُزيل.
  • التوقّف عند الحالة النهائية أو عند خطأ متكرّر تجاوز حدّاً معقولاً.

16.5 WebSocket كتحسين مستقبلي

إذا كثُر المستخدمون أو احتجنا تحديثاً فورياً حقيقياً، ننتقل إلى WebSocket. الملف التالي مكتوب كواجهة مخطَّطة فقط، وموضّح صراحةً أنه غير منفَّذ في الـ MVP، ويُذكر هنا لبيان شكل التحسين المستقبلي دون أي ادّعاء بإنجازه.

16.6 تنبيه: الفيديو المسجَّل ليس "نظاماً لحظياً"

دقّة الوصف

ما نبنيه هو تحليل فيديو مسجَّل (recorded video analysis)، وليس بثاً مباشراً. الـ Polling يُحدّث حالة معالجة ملف سبق رفعه، ولا يعني أن الكاميرا متصلة الآن. لا نستخدم كلمة "لحظي" أو "Live" لوصف هذه الوظيفة، لأن ذلك ادّعاء غير صحيح، والبث المباشر (RTSP) خارج نطاق الـ MVP صراحةً.

خلاصة الفصل 16

ما تعلّمناه

قارنّا Polling وSSE وWebSocket، واخترنا Polling للـ MVP لبساطته، وبنينا خطّاف useJobStatus يتوقف عند الحالة النهائية، وشرحنا تجنّب تسريب المؤقتات، ووضعنا WebSocket كتحسين مستقبلي غير منفَّذ.

ما يجب تنفيذه

  • استخدام useJobStatus في صفحة تفاصيل الفيديو.
  • التأكد من إلغاء المؤقت عند إزالة المكوّن.
  • ضبط الفترة الزمنية بحيث لا تُثقل الخادم.
  • وسم أي كود WebSocket بأنه مستقبلي وغير منفَّذ.

المخرجات المتوقعة

  • شريط تقدّم يتحرّك أثناء المعالجة ويتوقف عند الانتهاء.
  • لا طلبات متبقية بعد مغادرة الصفحة.
  • توضيح مكتوب أن النظام يعالج فيديو مسجَّلاً لا بثاً مباشراً.

كيف نتحقق من الإنجاز

  • افتح تبويب الشبكة: الطلبات تتوقف فور وصول الحالة النهائية.
  • لا يظهر تحذير تحديث حالة مكوّن غير مركّب في الـ console.
  • لا يوجد نص يدّعي اللحظية في الواجهة.

أخطاء شائعة

  • استخدام setInterval دون تنظيف فيستمر الطلب دائماً.
  • الاستمرار في الاستطلاع بعد الحالة النهائية.
  • وصف تحليل فيديو مسجَّل بأنه نظام لحظي.
  • فترة استطلاع قصيرة جداً تُثقل الخادم بلا فائدة.
